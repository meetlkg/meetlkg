Agent memory beyond the chat window

Testing Hindsight, Honcho, Letta, MemOS, SQLite, LanceDB and Qdrant for long-running agents: source retention, retrieval quality and the limits of a fast response.

THE SHORT VERSION

I need long-running agents to retain original history and select useful evidence for the next model call. Small pilots looked promising; larger tests exposed latency, matching and scope failures. Qdrant served a fully embedded 2.42 GB corpus within a 2 GiB database budget, but context selection still missed required sources. I am keeping the original archive, authoritative task state and replaceable retrieval indexes separate.

After comparing local agent harnesses on my DGX Spark, I kept coming back to context. A task could retain its transcript and still lose the evidence needed for its next step. I wanted to understand what I should actually put behind the memory layer of my Python harness, Unrig.

The most useful result was a distinction between retaining history, finding candidates and assembling the next prompt. My later Qdrant experiment served 2.42 GB of fully embedded source text within a 2 GiB database-container budget. It completed every timed request. It also missed important evidence. That combination shaped the architecture more than a product feature list did.

The use case: 100 agents, one growing execution history#

I am designing for a main conversational agent coordinating around 100 logical agents. Their work may run for days, with plans changing as results arrive. The combined messages and tool logs can reach several gigabytes. A separate external knowledge corpus could eventually exceed 300 GB; I have not qualified that size.

Consider an authorized security-testing workflow. Before retrying a probe, an agent may need the current target allowlist, an earlier tool result, a prerequisite from another agent and the receipt for a previous action. An old success does not establish current authorization. A missing receipt does not establish that a write is safe to repeat.

Keeping only the latest messages can lose those dependencies. Feeding every original message into each model call exceeds a finite context window. I want the originals preserved and a separate service that selects relevant, authorized source material for the next step. These experiments evaluate parts of that service, not 100 complete agents running simultaneously.

What I asked the memory tools to prove#

  • Retention: Can I read back the original message or log, byte for byte?
  • Retrieval: Can a query recover every required source, including buried diagnostics and causal prerequisites?
  • Selection: Do the returned sources actually make it into a bounded context packet?
  • Freshness and authority: Can the harness distinguish current constraints from superseded observations and enforce scope independently of a model?
  • Operations: What happens to latency, storage and recovery as the corpus grows?

A generated memory, a search snippet and an original source are different objects. A short recall response can be useful even when it does not contain the full passage. That is acceptable only if its references let the harness fetch the original material.

First, a small functional comparison#

I exercised four candidates locally on Linux ARM64. The common synthetic fixture had 120 events and five source-recovery questions. Its small profile contained 10,204 UTF-8 bytes; the large profile contained 2,170,204 bytes, with a diagnostic buried inside a long log. The padding was repetitive. This was a development smoke test, not a realistic capacity or reasoning benchmark.

Hindsight: the 5 GB ingestion eventually completed#

The next Hindsight workload used exactly 5,000,000,000 UTF-8 article-text bytes from 1,584,473 English Wikipedia documents. It was a source-lookup workload, not an agent-history workload. An earlier interruption and CUDA startup failures needed recovery, but they did not demonstrate a 5 GB storage limit. The completed audit found no missing, unexpected or mismatched original documents, and all 79 sampled source-API reads matched.

This was a pinned Hindsight 1.1.0 chunk-extraction profile with no extraction LLM, observations disabled, RRF retrieval and Nomic embed-text v1.5. PostgreSQL had a 12 GiB memory cap and eight CPUs; the embedding service had a separate 4 GiB CUDA allocator budget. It was not a qualification of Hindsight’s full learned-memory pipeline.

Those totals included approximately 110 MB of earlier pilot sources and tracing; they were not a clean per-bank amplification factor. Memory links, memory units and trace records accounted for much of the storage. This configuration did not meet my low-latency objective, even though source retention ultimately succeeded.

A paired comparison of simpler retrieval policies#

I then separated the original archive from the retrieval backend. The same Python controller could use recent history, SQLite FTS5, FTS5 plus Qdrant, or FTS5 plus LanceDB. In this paired experiment, the conversation evaluation used 30 LongMemEval question histories, four repetitions and a reference 8,192-token packet budget. The questions were initially held out from that pilot’s development split; they were reused in later work and are no longer an unseen evaluation set.

Both vector variants shared the same SQLite lexical branch. Qdrant used cosine HNSW; LanceDB used IVF_FLAT with 16 probed partitions. An exact-neighbor diagnostic measured 100% recall@32 for the configured Qdrant search and 71.77% for LanceDB at 16 probes. Searching all 128 LanceDB partitions reached 100%. This did not establish an intrinsic quality advantage for one database brand; the algorithms and recall settings differed.

There was another important limitation. The accompanying 5 GB log archive was fully stored and lexically indexed, but its semantic index contained only the first 1,024 characters of each event: about 1.024% of the raw bytes. Conversation embeddings also used prefixes of source pieces. That experiment could evaluate the controller and partial-card approach. It could not establish full semantic coverage of 5 GB.

Qdrant with every source chunk embedded#

For the next run, every retained chunk went to the real embedding model in full. There were no prefix cards, model-written summaries or random vectors substituting for the source. The planned log corpus was 5 GB across 100 worker identities. I stopped bulk ingestion at 2,407,443,115 committed bytes and measured that checkpoint. The original full archive stayed intact.

The 15,309,333-byte conversation fixture had been queued after the logs, so it was added separately for semantic queries. The final measured corpus was 2,422,752,448 source bytes and 1,197,544 evidence vectors. I rebuilt the lexical index over exactly that same frozen prefix, rather than compare a 2.4 GB vector index with keyword search over the original full 5 GB.

Qdrant 1.20.0 retained a 2 GiB container limit and four CPUs, with on-disk vectors, graph and payloads. The shared Nomic embed-text v1.5 service used GPU FP16, 768 dimensions and a separate 2 GiB CUDA allocator budget. The source was split into non-overlapping 2,048-character parts; actual tokenizer inputs above 2,048 tokens were rejected rather than truncated. These were component budgets on a GB10 development host with roughly 122 GiB system RAM, not a 2 GiB total deployment.

Every stored chunk reference matched its original source, and 101 sampled stored vectors matched cached model outputs. Building the search graph to 99.8% indexed took 523 seconds. A real container restart preserved the checked evidence and point count. None of these checks establishes retrieval relevance by itself.

The corrected run completed 6,570 timed requests with zero request errors or observed scope violations. Service time includes query embedding, Qdrant retrieval and original-source validation; it excludes queues and final-model generation. Four operations were admitted at once. The whole-collection conversation profile submitted a 90-request burst. The mixed scoped profiles submitted 1,050 requests; their 100-worker dense burst had a queue-inclusive p95 of 19.73 seconds. These different burst sizes must not be pooled.

The Wikipedia and agent-history runs used different corpora, vector counts, retrieval policies and resource profiles. I do not calculate a Hindsight-versus-Qdrant speedup from their latency tables. The paired pilot also used different chunking and selection budgets from this later run, so its accuracy numbers cannot be treated as a controlled before-and-after comparison.

Conversation counts require every annotated source session to be represented, not a correct generated answer. The stricter requirement to recover every annotated original piece passed 23/30 scoped questions at eight parts, and 28/30 at 32 candidates. Merely finding a passage in the right conversation can overstate how much useful evidence was recovered.

Keyword search found all 30 standalone checkpoint identifiers and all 100 distributed hashes. Its remaining 30 misses were identifiers embedded inside larger tokens. The configured word tokenizer did not provide arbitrary substring matching. Dense retrieval did not repair those global misses. I need explicit identifier matching and a separately tested substring path; calling everything “semantic memory” would hide that requirement.

Naive reciprocal-rank fusion also reduced scoped conversation session coverage from 28 to 25 questions. Combining two rankings was not uniformly helpful. Query type, scope, duplicate material and the final candidate budget deserve their own evaluation.

I found a scoring error while reviewing the first results: 20 hashes crossed two adjacent returned chunks. Requiring the full hash to appear inside a single chunk counted those recoveries as misses. I corrected the scorer to join only consecutive returned parts of the same gold source and piece, added regression tests against missing or foreign parts, preserved the earlier reports and reran all nine timed profiles. The tables here use the corrected run.

Approximate search has its own recall tradeoff#

The timed profiles used HNSW ef=128. In a separate 15-query development probe, I compared higher search effort with exact cosine results. On four all-agent log probes, mean exact-neighbor recall@32 rose from 33.6% at ef128 to 89.1% at ef2048. Mean search-only time rose from 85 to 844 ms. The eight narrow agent/mission probes matched exact results at every tested effort.

Those are tiny sequential diagnostics, not concurrent p95 guarantees. They show that a fast ANN response can omit actual nearest neighbors. They also separate ANN recall from useful evidence: exact search still missed required evidence at eight parts for two of the three global conversation probes. Raising search effort alone would not finish the context selector.

Collection storage after indexing was 4.86 GB logical, or 4.47 GB allocated, excluding original sources, FTS and staging caches. The experimental vector cache added 3.68 GB. Qdrant reached its configured memory cap with cache reclamation and no OOM kill; the largest benchmark-client RSS was about 179 MiB. Model CPU memory, CUDA context and host caches were additional. I have not demonstrated the whole system on a small desktop.

The context service I am building from this#

I am keeping the authoritative execution record separate from replaceable retrieval indexes. SQL remains useful for task state, receipts, revisions, permissions, source offsets and durable indexing work. Immutable artifacts retain original messages and logs. Neither a vector index nor a utility model gets to become the authority for current permissions or whether an action already happened.

  • Pin mandatory state directly. Current constraints, workflow revision and unresolved effects must survive a poor retrieval ranking.
  • Narrow the search first. Use the authorized mission, agent, time and task dependencies before applying candidate limits.
  • Route the query. Identifiers, natural-language questions and code navigation need different retrieval paths. Evaluate fusion rather than assuming it helps.
  • Fetch originals after candidate selection. Keep source IDs, ranges and digests; expand related tool responses and causal parents within a budget.
  • Expose lag and incomplete retrieval. A failed or delayed index must not make a newly recorded constraint disappear. This remains an integration requirement, not a guarantee established by the immutable-corpus benchmark.
  • Keep model selection advisory. An optional helper can propose candidates, while deterministic checks enforce scope, required state and token limits.

I also screened a CPU-only Qwen3:0.6b utility selector on six questions. Its service p95 was 27.99 seconds with two fallbacks. That small, mixed-cache screening rejected that configuration as a mandatory low-latency stage; it did not establish that all small-model selectors fail. I want a measured quality benefit before paying that cost on every context request.

For durable workflows, I would put source references and task revisions into Temporal history and fetch large context through activities. The archive and context service would preserve the source independently. The eventual 300+ GB external knowledge corpus would have a separate ingestion and capacity policy from running-agent history.

Code retrieval needs another evaluation#

These runs do not qualify codebase retrieval. Fixed character chunks can split a function, identifier or its surrounding imports. A code path needs syntax-aware units, repository/commit/path/line metadata, exact symbol lookup and an embedding profile evaluated on code. The Qdrant code-search guide describes parsed code structures and separate text/code embeddings; it does not make our text benchmark a code benchmark.

Where I have reached#

The evidence supports Qdrant as a workable retrieval component at the measured 2.42 GB size under the tested database budget. It also gives me concrete failures to fix in matching, scope selection, ANN effort and context assembly. SQLite remains useful in the architecture, and LanceDB remains a candidate for a matched-recall desktop comparison. I have not selected a universal winner among memory frameworks.

The full 5 GB Qdrant gate, code retrieval, a 300+ GB external corpus, changing-source consistency and month-long runtime reliability remain open. My next tests need fresh realistic missions, source-level correctness, concurrent writes, cold-cache behavior and the actual target hardware. The useful outcome so far is a context-service boundary I can test independently of the main agent.

The aggregate results and dataset/model pins accompany this article. They document the measurements, source-artifact hashes and limitations. Raw histories, model weights and the internal runner are not included, so this is not a turnkey independent reproduction package. The measurements were collected in October 2026 on a shared development host; offline verification overlapped late profiles in the corrected run.

A few useful questions

Did Qdrant pass a fully embedded 5 GB test?

No. Bulk ingestion stopped at 2.407 GB of committed logs. A 15.3 MB conversation fixture was then added, giving a measured 2.423 GB corpus. The full 5 GB gate remains open.

Was the whole system limited to 2 GiB of memory?

No. That limit applied to the Qdrant container. The embedding service had a separate CUDA allocator budget; model CPU memory, clients and host caches were additional.

Did these experiments measure correct LLM answers?

No. They measured original retention, required-source recovery, approximate-neighbor recall and retrieval latency. Finding a source session is weaker than recovering every annotated message or generating a correct answer.

Can I use the same results to choose a code-search system?

No. Code retrieval needs syntax-aware chunks, repository and revision metadata, symbol lookup and a separate code evaluation.
